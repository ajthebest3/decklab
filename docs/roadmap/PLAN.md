# DeckLab — five-phase product and learning upgrade

Draft for five independent Mirai reviewers · 13 November 2026

## Outcome and scope

Build a coherent, attractive research and paper-trading product across the website and native Android app: fast exploration, understandable evidence, trustworthy controls, resilient private connections and a learning process that can be evaluated rather than merely described as intelligent. This document is a specification, not an implementation or a profitability claim.

The owner requested detailed planning, a slick graphical redesign, review by five strong models including Fable and Astra, and permission for the reviewers to propose changes to any part of the plan, including the learning algorithm. Reviewers can revise the specification; they cannot change financial settings, start workers or execute code. Current source is the baseline, not the old screenshots or historical running notes.

### Non-negotiable constraints

- DeckLab remains paused. The new-server owner pause supersedes all historical automatic resumes. Planning API calls are finite, explicitly requested reviews, not resumed scheduled research. Publication and a later trading/research Start are separate decisions.
- Preserve the original account, archive and managed population as separate histories; all fills, losses, fees, funding, rewards, lineage, source evidence and existing signing/admin identities survive. Never create a clean-looking performance history by deleting losses.
- Freeze current saved trading controls and routes until a specific proposed change is reviewed. Do not restore historical defaults from an old note. Risk changes need a before/after diff, rationale, isolated validation and explicit owner authorization before activation.
- Models receive sanitized public-market context and point-only strategy feedback. Owner-only monetary evaluation stays outside trading prompts. Website/API keys, admin tokens, SEC contact and private device information never enter review prompts, logs, browser bundles or APKs.
- Paper execution remains deterministic and evidence-backed. No broker integration, real-money orders, invented liquidity, synthetic fills, unsupported-market trading or claim of guaranteed returns.
- Keep the current private loopback/Termius access model. Do not expose the server publicly as a side effect of redesigning its connection flow.
- Use the existing buildless web stack and native Java app incrementally. No compulsory framework rewrite, second ledger or parallel executor. New dependencies require a concrete benefit, pinned versions, license/security review and an exit path.

## Evidence baseline

Already implemented: Mission control; scanner and charts; source-backed market discovery; watchlists/notes; bot and journal views; market-evidence drilldowns; Mirai settings/model catalog; passkey-gated Codex Admin; native Android Views/Canvas and private SQLite cache; optional specialist WebView; Day Trader pipeline. These are improvement targets, not missing features.

Observed source gaps: the website's sidebar Emergency stop changes only the original-account kill switch; a successful state request becomes a broad ENGINE ONLINE badge; route refreshes and several panels rebuild content; Mission control truncates results without paging; Day Trader exposes much of its output as raw JSON; refreshing model settings can discard unsaved edits. Native typography/accessibility and per-resource failure reporting need attention. Source-level hypotheses require focused tests before implementation claims.

At audit time market-deck.service is masked, with no port8790 listener. Historical test counts and model-probe success are not new-release validation. No current profitability or handset verification is assumed.

## Phase 1 — truthful controls, private connection and safe foundation

**Outcome:** the owner can tell what is running, what data is fresh, which account a control affects, and what a connection failure means. P1 gates all subsequent runtime changes.

### P1.1 Preservation and current-state inventory

Record source revision and local-diff manifest without resetting the dirty workspace. Snapshot service masks, pause markers, timer definitions, relevant settings, schemas and APK identity. Use SQLite backup APIs for consistent copies if the service is ever active; hash originals and backups. Define immutable-row assertions and reconciliation for funding, reservations, fills, fee-scenario audit and terminal rewards. Exclude secrets from reports. Record all current setting values privately and use them as the migration baseline.

### P1.2 Mirai connection and model capability registry

The new credential has a separate private configuration and authenticated catalog access. Plan a deliberate promotion into DeckLab through its existing private credential store only after a successful short completion and confirmation of intended scope. Preserve existing fallback credentials, provider routes and pause state. Store a key fingerprint, never key text, in diagnostics. Distinguish catalog-listed, completion-verified, schema-verified, failed and expired verification states. Reverify when a credential, model route or prompt schema changes. Add request budgets, bounded concurrency, timeouts, cancellation, backoff and explicit cost/usage reporting where the provider actually returns it. No invented dollar estimate when pricing is unknown. Preserve drafts during catalog refresh and show assignment diffs before save.

### P1.3 Stop semantics and control isolation

First rename existing actions to their actual scope: original account, archive, managed population, research and the full service. Show whether each action stops new entries, automatic exits, queued work or all processing, and that a stop does not liquidate holdings. Keep the owner pause visible above per-engine status. If an aggregate stop is added, use a durable command ID, deterministic engine targets, per-engine acknowledgements and partial-failure reporting; never claim atomic success across independent databases. Reconcile after lost acknowledgements and display unresolved targets. A later Resume must enumerate exactly what it will re-enable and never clear risk brakes implicitly.

### P1.4 Status and connection contracts

Introduce a versioned capabilities/readiness response separate from a cheap liveness probe. Include backend build/schema compatibility, selected origin, service/owner-pause state, per-resource last attempt/success, clock skew, source timestamp, receipt timestamp and stale threshold. Separate server reachability, feed freshness, executable-book freshness, FX, model availability and paper-engine state. The client displays paused, disconnected, stale, partial and healthy states distinctly. Preserve source-specific session/calendar semantics; US-session rules never control NSE or crypto. No data response is presented as newer because the UI refreshed.

### P1.5 Private origin and operation safety

Keep explicit endpoint validation, Host/Origin protection, bounded requests and API allowlists. Tie confirmations to origin, account, settings revision and command ID; changed origin/revision invalidates the review. Add rate/size limits for model and admin requests, structured redacted errors and request IDs. Expired admin state stays locked; no passkey reset or Codex thread rebinding. Never queue financial mutations offline. Read-only recovery checks cannot start a service.

**Files:** `server.py`, `mirai_client.py`, `population_controls.py`, `static/app.js`, `static/ai-settings.js`, Android `Connection.java`, `DeviceRepository.java`, `MainActivity.java`; new narrow diagnostics/contracts modules if justified.

**Acceptance:** all protected histories/identities unchanged; current pause/masks unchanged; scoped and partial stops accurately reported in isolated tests; invalid/stale model responses rejected; no credentials in output; old clients receive a clear compatibility result; origin-switch and lost-ack tests cannot duplicate a command. **Rollback:** revert new code and additive nonfinancial metadata while retaining every audit record; never restore an old financial DB over new legitimate events.

### P3.3 Per-resource repository and connection recovery

Represent each resource with cached value, freshness, request state, last error and next eligible retry. Distinguish queue rejection from server failure; no silent drops. Coalesce reads, cancel obsolete symbol/origin work and maintain a small bounded priority queue. Foreground refresh is visibility-aware and backs off on repeated errors. ## Phase 4 — evidence-first research, five-model planning desk and learning redesign

**Outcome:** useful model collaboration and a measurable learning experiment, with strict separation from execution and owner-only evaluation.

### P4.1 Research and Day Trader workflows

Convert existing raw output into entry-status, stop/target, whole-share affordability, risk/reward, replay probabilities and assumptions cards. No entry trigger means downstream stages say Skipped/waiting, not a fabricated ticket. Show path count versus number of real historical sessions separately:10,000 simulated paths are not10,000 independent observations. Display underlying-versus-tokenized mapping, quote times, source limitations and market/session scope. Add scenario comparisons, bookmarked evidence and an advanced raw-data view. A saved plan remains a planning artifact, with no execution bridge added.

### P4.2 Five-model planning/review desk

Use durable draft revisions and a bounded five-reviewer workflow only on explicit request. Show each actual request's model/role, queued/running/error/verdict state and timestamps. Reviewers propose structured changes; a merge produces an inspectable plan diff and attribution. Disagreements are retained, not averaged away. Never describe consensus as market truth or guaranteed edge. Invalidation is hash-based: any material edit after sign-off reopens affected reviews. Cache exact completed reviews; prevent duplicate submissions after uncertain provider responses. Actual model requests consume budget; timed-out calls retain unknown billing state. Trading observations and original admin channel remain separate.

### P4.3 Current learner and proposed replacement

Current terminal rewards are+1/-5/0 and context Q uses an exponentially weighted update. This is strategy adaptation, not deep RL or model-weight fine-tuning. Exact strategy hashes help attribution but can produce sparse cold starts; retrospective range-versus-fee filters are not predictive edge estimates.

Source audit details: `demo_learning.py:21–29` uses alpha0.2; the managed context adds symbol/family/full strategy hash (`population_engine.py:398–405`). Excluding neutral outcomes, positive expected+1/-5 points requires a win rate above83⅓%, which is not equivalent to positive monetary expectancy. Show that objective mismatch explicitly. Existing Q-based sizing and all effective saved controls remain the baseline; a new reward mapping is a separate owner-reviewed experiment, not a quiet change to legacy labels.

Propose a versioned, conservative contextual policy experiment rather than immediate replacement. Keep the current deterministic engine and current risk controls as the champion baseline. Define a small interpretable feature set from information available at decision time: lagged return/volatility, spread, depth/participation, volume, trend/range regime, source coverage, session and market class. Normalize using training-window data only. Candidate actions select among pre-approved bounded strategy templates or abstain; learning cannot change cash, leverage, hard limits, order semantics or exit rules. A hierarchical shrinkage estimator with confidence bounds is the initial candidate; more complex bandits are optional only if simple baselines are beaten. Avoid an opaque deep-RL rewrite without sufficient evidence.

### P4.4 Reward, attribution and policy invariants

Retain immutable legacy point outcomes and introduce a separate versioned experiment reward derived from allowed terminal points and nonmonetary safety signals. The evaluator can separately compute fee-adjusted monetary metrics, calibration and downside outside trading prompts. Each candidate episode records decision ID, exact feature/asof/source revisions, model/requested+returned route, prompt/strategy/policy/schema versions, eligibility gates, action probability if applicable and pinned exit plan. No duplicate reward on partial exits or additions; unresolved/stale episodes do not become wins. Do not let a model grade its own strategy or produce its own successful outcome evidence. Cross-model lessons remain candidate suggestions until independent evaluator gates pass.

### P4.5 Replay, holdout and promotion

Audit whether historical snapshots actually support replay; record unavailable intervals rather than filling gaps from future data. Use chronological train/validation/locked final test, with purging/embargo for overlapping episodes and grouped market/session regimes. Fit transforms and feature selection within training folds. Compare abstain/cash, fixed simple strategies, frozen current policy and candidate on identical eligible events and execution-cost assumptions. Record trial count and prevent repeated tuning on the final holdout. Report net expectancy, downside/drawdown, turnover, costs, coverage, exposure, calibration and uncertainty; insufficient independent sessions means inconclusive.

Replay must preserve later-book execution, shared liquidity, lot/minimums, FX/session validity, delay and partial-fill rules; current internet snapshots cannot reconstruct a missing historical book. Off-policy metrics are valid only with required action support/propensities, never a substitute for missing evidence. Promotion sequence: offline-only evaluation → shadow proposals with zero order authority → bounded paper canary only after separate owner Start → monitored comparison. Exact numeric evaluation gates must be preregistered after a coverage/power study, not invented as a universal number of trades. Freeze the final test before outcomes are examined. Drift, provider changes, source errors or uncertainty trigger abstention/demotion, never relaxed limits.

Capture the entire eligible opportunity set, including abstentions and rejection reasons, not just selected orders. Reconstruct only feedback/lessons/headlines available at that historical moment. Correlated bots are not independent experiments; use time/session/symbol clusters for uncertainty and declare the multiple-comparison scope. Record unresolved episodes, exposure and pause intervals separately to avoid closed-trade survivor bias. Historical episodes affected by prior management/fee changes remain labelled cohorts.

### P4.6 Learning dashboard

Show champion/candidate versions, training/evaluation windows, sample independence/coverage, point outcomes, reviewer dissent, feature definitions, source gaps and uncertainty. Keep funding separate from returns, historical fee scenarios separate from as-executed facts and in-sample results separate from out-of-sample/shadow results. A “Learning” animation reflects persisted jobs only. Owner-only evaluator data cannot leak through exports, tooltips, generated summaries or research-context builders.

**Acceptance:** no production policy change during planning; deterministic replay fixtures; point/P&L leakage tests at every prompt builder/export; no lookahead and no double rewards; baseline comparisons reproducible; model identity/errors preserved; final holdout remains untouched until frozen; failed or inconclusive candidate cannot replace champion. **Rollback:** retain champion policy and model routes, demote only the experiment, keep all experiment/evidence records; never rewrite historic Q/points to imply success.

### C3 — visual, gesture and accessibility acceptance (phases2/3/5)

Web target is WCAG2.2 AA with manual journey checks, not just an automated scan. Text must meet4.5:1 against its rendered background, or3:1 for large text under the standard's size/weight definition. Meaningful UI boundaries/icons/chart marks and focus indicators meet at least3:1. Record each meaningful color pair and rendered ratio in both themes; failing muted labels/accent text are revised. Disabled controls still have an understandable textual availability state. Loss/gain and series differ through label/shape/dash/texture as appropriate. Meaningful chart grids/axes stay legible; decorative low-contrast details cannot carry information.

Charts default to ordinary page scrolling on touch. An explicit tap/button activates chart interaction, with a visible active state and a reachable Exit chart control; an ordinary vertical swipe outside inspection mode scrolls the page. In active mode horizontal drag pans/inspects, pinch zooms, and long-press or an explicit Inspect control opens the crosshair/value readout. A deliberate vertical scroll gesture relinquishes chart capture so the page is never trapped; gesture thresholds and pointer cancellation are documented and tested. Keyboard controls and a full accessible data table provide equivalent exploration. Accessible table paging announces visible/total positions and reaches the entire filtered set, not just the virtualized DOM window.

Each modal drawer/dialog sets initial focus, contains focus while modal, supports close/back and restores focus to its still-valid trigger. Nonmodal details do not trap focus. ### C4 — reproducible candidate algorithm v0 (phase4)

This is a proposed OFFLINE experiment, not the deployed learner. The initial experiment retains terminal+1/-5/0 as its exact target, while the owner-only evaluator separately reports financial expectancy and the objective mismatch. New monetary rewards are outside v0 and need a separate version/specification. Safety signals are hard eligibility vetoes, never an additive reward that a learner could trade away for points.

**Unit and labels.** An episode is the existing full-position lifecycle under the admitted pinned strategy/exit/policy version, including additions/partial fills until final closure. One immutable episode ID yields at most one mature label. Positive/negative/neutral uses the existing terminal label under its explicit historical fee basis; we do not relabel legacy outcomes. A label becomes available at its recorded closure-and-validation time, never the original entry time. Open, stale, unresolved, interrupted or right-censored episodes have no mature success label; their exposure and censoring count remain visible. A risk/event veto excludes future action eligibility but does not delete adverse episode evidence. Unsupported book coverage is permanently labelled replay-unsupported for that frozen dataset, with counts and exclusions reported. A separately versioned signal-only cohort may be studied but is never mixed into execution-outcome evaluation.

**Population and features.** The logged eligible opportunity set is defined by the unchanged deterministic market/data/risk gates at each decision time. Features are predeclared, lagged and versioned, using provider-capture availability times and revision IDs for price, volume, spread, depth, session, regime and lessons/headlines. Backfilled/corrected data cannot appear before its actual availability. Group candidates by venue, preapproved template/family and frozen feature bins; retain the exact strategy hash in provenance. Do not assume labels for unchosen actions: historical selected-action evidence supports only its observed action/context. Counterfactual labels require a separately declared replay with sufficient later-book evidence, hypothetical-action attribution and shared-capacity assumptions; they are not actual fills.

**Estimator.** For a context/action c with matured counts `n_plus,n_minus,n_zero`, estimate a three-outcome distribution using additive shrinkage toward a same-venue/same-template parent computed from the training partition only, excluding local c to avoid counting its observations twice. Root parent uses symmetric Dirichlet(1,1,1) smoothing; initial parent concentration is20 pseudo-observations, fixed in the preregistered v0. Posterior-mean probabilities are `(n_k+20*p_parent_k)/(N+20)`, and point score is `p_plus−5*p_minus`. Pseudo-counts are not observed samples and are labelled as such. No cross-venue/template pooling or future/test outcome updates. Zero/unsupported local action support cannot produce an admitted candidate merely from the prior.

**Uncertainty and choice.** Refit the complete training estimator in a deterministic seeded2000-resample moving-block bootstrap, with block/session/symbol cluster specification fixed by the coverage study. Candidate selection uses a one-sided95% lower bound on expected points, with candidate-family simultaneous-error adjustment declared in the preregistration. Eligibility also requires the preregistered effective independent-session/support minimum. If confidence cannot be estimated, coverage/support is insufficient, a health/risk veto fires, or no candidate has a strictly positive adjusted lower bound, abstain. Otherwise rank eligible candidates by that bound; exact ties use a stable template ID. Execution sizing remains the current deterministic control path. This conservative point objective may abstain almost everywhere; that is an acceptable v0 result, not a reason to weaken limits. Compare the shrinkage candidate, unpooled simple estimator and frozen EWMA as ablations. None is promoted merely for superior in-sample points.

**Replay time.** At every simulated decision, only previously matured labels/lessons and contemporaneously available source revisions may update state. A frozen-policy comparison disables updates for both policies; a separate online-adaptation replay permits causal updates identically for both. Every mode has its own manifest. Perturbing future observations/labels must not change earlier features/actions. Repeatability fixtures include partial closes, additions, duplicate rewards, unresolved trades, neutral outcomes, zero support, all losses, correlated sessions, no book and source revisions.

### C8 — operational statistical protocol and remaining contract precision (phases1/3/4/5)

The following sharpens C4/C5; it does not claim that historical data satisfy its requirements. Until every manifest field and diagnostic passes, all candidate intervals are exploratory/unavailable and no confirmatory or promotion claim is permitted.

**Partitions and outcome-blind feasibility.** First build an availability-only catalog with capture/session IDs, timestamps, field-presence indicators, declared template horizons, source revision metadata and file hashes. Expose no prices/returns, rewards, P&L, action success, outcome-derived exclusions or performance summaries to the feasibility runner. Log EVERY feasibility query with partition, purpose, protocol hash and returned schema; reject non-allowlisted outcome fields. Count the complete captured UTC-date grid, including dates with missing eligible data, to avoid selecting profitable days. On that frozen grid use the first60% of dates for training, next20% for validation and last20% for the locked test, with boundaries rounded down to whole UTC days and fixed in the manifest before outcome access. Insufficient dates or support yields inconclusive rather than moving boundaries after inspection. Symbol/venue cohorts are preregistered and use the same chronological boundaries across all bots; no random row split.

Define `H` as the maximum permitted decision-to-label horizon across registered templates, including documented maturity delays, and `L` as the maximum feature lookback. The information interval for each opportunity is `[decision_time−L, decision_time+H]`. Keep a labelled episode only when its entire information interval and actual mature-label timestamp lie inside one partition. Purge the crossing episodes and apply an additional `H+L` embargo on either side of each train/validation/test boundary. Paused/unresolved lifecycles exceeding H are censored/unlabelled in that protocol, reported separately and cannot count as successes; do not redefine H after seeing their outcomes. Replay modes treat these episodes identically for champion/candidate. Record exclusion IDs/counts and source-coverage cohorts before results. Actual selected-action, hypothetical replay and signal-only cohorts have separate model inputs/results and are never pooled for promotion.

**Dependence and resampling.** Base time units are UTC days containing ALL symbols, venues, bots and opportunities, preserving cross-sectional/common-news dependence. Set moving-block length in days to `b=max(7,ceil(2*(H+L)/86400))`, fixed before outcome inspection. Expand block boundaries until every overlapping information interval is assigned wholly within its block; overlapping candidate episodes and repeated bot decisions from one opportunity are kept together. If this collapses into too few disjoint effective blocks, the interval is unavailable and the policy abstains. Effective support counts these independent block units, not bot count or bootstrap draws. Neutral matured labels count once in N and in raw episode support; they do not create additional block support. N equals `n_plus+n_minus+n_zero`; pseudo-observations never count toward support. Every resample draws whole contiguous blocks with all associated symbols/venues/actions and refits the complete shrinkage estimator; no row/bootstrap-per-bot shortcut is allowed. Raw counts, effective block support, right-censoring and repeated-opportunity clustering are reported separately.

**Multiplicity and calibration.** Freeze the complete family K of candidate/template/context-action comparisons and registered modeling variants before confirmatory outcomes; count rejected/failed variants as trials. For this initial conservative protocol use Bonferroni one-sided tail probability `0.05/K` for the simultaneous lower bounds, with deterministic tie-breaking and `B=max(2000,ceil(20*K/0.05))` resamples to give a finite tail-resolution target. This is a declared conservative procedure, not a proof that bootstrap assumptions hold. Training/validation-only diagnostic fixtures with known correlated/overlapping synthetic processes and null actions must show acceptable interval coverage/false-selection behavior under a preregistered tolerance; include long-range dependence and sparse-action stress cases. Failing calibration, insufficient effective blocks or tail resolution makes bounds exploratory/unavailable and blocks confirmatory use; no numerical positive bound overrides this failure. Synthetic fixtures validate estimator behavior only and never become trading evidence.

The root prior and concentration20 are fixed v0 choices; alternative prior sensitivities are separately registered exploratory train/validation variants and included in trial accounting. A positive point-score bound does not establish positive financial expectancy or a trading edge. Financial, missing-outcome, fee/delay/shared-capacity and replay-coverage sensitivity analyses remain separate owner-only reports with their cohorts and assumptions.

**Confirmatory lineage.** Each candidate references its parent experiments, every prior validation/confirmatory query, all retired partitions and the feature/prompt/template/protocol lineage. A final-test evaluation covers the preregistered family as one query with all results retained. Outcome-informed revision retires the partition for ALL descendants sharing that knowledge; later fresh periods require a new lineage manifest and explicitly limited claims. No dashboard/reviewer feedback can make an inspected period unseen again. Data-custody checks and future-data-perturbation fixtures verify the partition/purge/embargo and outcome-blind schema rules before evaluation.

**Other accepted precision.** Server contracts define per-resource stale thresholds, source/receipt age and clock-skew handling; clients do not invent conflicting thresholds. Paused/offline clients explicitly show last-known thresholds/ages and current availability. If optional cross-device condition acknowledgement sync is later built, preserve per-device audit history and surface merge conflicts; no last-write-wins erasure. Every changed route's machine-readable contract hash is bound into the release manifest; mismatch blocks the affected release gate.
